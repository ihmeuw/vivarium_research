=========================================================
Data version control
=========================================================

.. contents::
   :local:
   :depth: 2

Current practice
----------------



Design
------

All inputs, intermediates (including artifacts), and outputs would be tracked within Git (i.e. would get committed and included in PRs,
you could switch between versions with ``git checkout``, etc).
Since there is a size limit on files that can be pushed to GitHub, the larger files need to be stored somewhere else.
From a user's perspective, this should be seamless: when running a ``git push`` command, the small files would be pushed to GitHub
and the large files would be pushed to the alternate location.

Capacity management ("eviction")
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

If we no longer had space to store all past versions of large files, we would run a tool (that we would develop internally) that would follow this pattern
to delete the files we are least likely to want in the future:

1. Delete all files that are generated by steps in the workflow, before deleting any files that are (or contain) top-level inputs to the workflow (straight from GBD or elsewhere).
2. Within each of those categories, delete all files that are not referenced by any commit with a branch or tag pointing to it, before deleting any files that are referenced by a branch or tag.
3. Within each of those categories, delete files in order from oldest to newest, based on the date of the last commit that references them.
4. Break ties by deleting larger files first.

We would do the minimal pruning; in other words, we would delete files in this order only until we were within our storage capacity budget.
